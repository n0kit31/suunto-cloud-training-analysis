# Suunto Cloud backend migration assessment

Keep Python for the backend. If profiling shows FIT ingestion is a material bottleneck, pilot a Go decoder behind the existing Python entry point. Compare it with an in-process Garmin Python SDK adapter and the pinned Node decoder before choosing. Treat Go as the first migration candidate, with Rust as another candidate for a measured CPU or memory constraint. Consider PHP if there is a concrete deployment or maintenance reason. This assessment is based on source review. The performance ranking and decoder parity are open questions.

## What a migration would change

- **Suunto access.** Suunto requires an OAuth authorization-code exchange and a Developer API subscription key for integration requests. Its Developer API is rate-limited. The current Python client serializes refresh across processes, persists rotated tokens, retains the previous refresh token when the response omits it, and replays an authenticated read once after a 401. The bridge maps rate limits and other failures to structured errors. The TypeScript store owns durable job deferral for rate limits and bounded retries for transient network failures. Preserve those responsibilities and verify the delay-seconds and HTTP-date forms of `Retry-After`. A new HTTP client can implement the same policy in any of the four languages. [Suunto integration setup](https://apizone.suunto.com/how-to-start), [Suunto API FAQ](https://apizone.suunto.com/faq), [HTTP Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after), [Python access layer](../suunto_cloud/authentication/access.py), [Python bridge](../suunto_cloud/web_bridge.py), [TypeScript job store](../web/server/store.ts).
- **FIT decoding.** The current Python path launches Node with the pinned `fit-file-parser` 1.20.0, writes decoded JSON, and reads it back for analysis. The same parser loader is used for GPX export. Measure decoding, subprocess startup, and the JSON handoff individually. A decoder-only change can leave GPX on its current path until its own parity is established. [Dependency pin](../package.json), [Python decoder wrapper](../suunto_cloud/fit/__init__.py), [Node FIT decoder](../suunto_cloud/fit/decode.cjs), [GPX export](../suunto_cloud/fit/export_gpx.cjs).
- **Metrics and charts.** Python applies timer and pause semantics, selects laps, computes exercise metrics and SuuntoPlus channel summaries, and generates SVG and interactive HTML. Porting this logic would require preserving units, weighting and rounding, missing-data behavior, pause handling, chart series and axes, localization, and browser interactions. Keep this logic in Python for a decoder pilot and use the existing synthetic tests to check downstream results. [FIT analysis](../suunto_cloud/analysis/fit.py), [Metrics](../suunto_cloud/analysis/metrics.py), [Chart model](../suunto_cloud/reporting/chart_model.py), [Interactive chart renderer](../suunto_cloud/reporting/interactive.py), [Synthetic fixtures](../tests/fixtures.py).
- **TypeScript worker.** The worker invokes `python3 -m suunto_cloud.web_bridge` through `execFile`. It already handles JSON responses, cancellation, timeouts, a stdout size limit, and validation of the result and artifacts before publishing through the SQLite store. It requests a 30-day window on the first synchronization and uses a modification watermark with overlap on later runs. The worker and bridge coordinate request pacing with a 6.5-second interval. A later bridge replacement can use the same process interface for list, analysis, device model, and auth/settings commands. Preserve arguments and stdin, stdout JSON and structured errors, timestamps and units, workspace artifacts, lease and cancellation behavior, and the credential mount boundary. A decoder pilot only needs the internal FIT boundary. [Worker](../web/server/worker.ts), [Bridge](../suunto_cloud/web_bridge.py), [Web deployment](web.md).

Moving Cloud access, analysis, and reporting into that runtime could remove the bridge subprocess and Python dependency from the web deployment. The Python CLI would still need an explicit compatibility decision.

## What counts as FIT compatibility

Garmin lists official FIT SDKs for Python and JavaScript, among other languages. Go, Rust, and PHP candidates here use third-party decoders. Suunto API proficiency concerns account authorization, downloads, pagination, limits, and recovery. Decoder correctness concerns the binary file and its normalized values. Assess decoder speed only once candidates produce equivalent results. The Go project's published comparison explicitly excludes developer data and unknown messages, so it provides no timing for the SuuntoPlus workload. [Garmin SDK language list](https://developer.garmin.com/fit/), [Go decoder benchmark](https://github.com/muktihari/fit#benchmark).

Garmin identifies a developer field by the pair of developer data index and field definition number. Suunto documents float32 channel samples on `record` messages and summary values on `session` messages. The display label and format are themselves developer fields attached to `field_description` messages. Preserve app identity, names, units, values and placement through decoding, including duplicate names across apps. Check Suunto's documented multisport omission and the application's existing single-session upload policy independently. The current Python summary consumes normalized labels and field names, so verify the raw identity before flattening the result and explicitly test collisions. [Garmin FIT protocol](https://developer.garmin.com/fit/protocol/), [Garmin developer-data cookbook](https://developer.garmin.com/fit/cookbook/developer-data), [Suunto FIT description](https://apizone.suunto.com/fit-description), [Suunto's decoding example](https://apizone.suunto.com/fit-developer-fields-decoding-example-code), [Current metrics consumer](../suunto_cloud/analysis/metrics.py), [Web upload behavior](web.md).

## Staged parity benchmark

1. **Establish the baseline in Docker.** Use generated FIT files, synthetic decoded fixtures, and a local stub for Suunto HTTP responses. Build small, typical, and long activities plus a batch import. Time request waits, FIT decode, normalization and JSON I/O, metrics, chart rendering, subprocess startup, and the full worker job separately. Record warm and cold latency, median and p95, throughput, CPU and peak memory for the process tree, and bytes written. Pin decoder/profile versions, runtime versions and build modes, container resources, fixture seed and hashes, and repetition count. Keep the measurements comparable across candidates.
2. **Check binary and normalized parity.** Generate FIT 1.0 and 2.0 fixtures with known expected values. Include compressed timestamps, endianness and local definition changes, scaled and invalid values, missing channels, native overrides and unknown messages, truncated files, bad CRCs, and single- and multi-session examples. Include two synthetic app identities with overlapping field numbers and names, nested label and format fields, missing and zero values, record samples, and session totals. Assert message counts, order, timestamps, units, identities, native/developer precedence, and errors. Derive expected values from the fixture inputs and published specs, then cross-check with a Garmin SDK or FitCSVTool and Suunto's reference logic. Keep differences from the current decoder visible and adjudicate them against the fixture contract. [FIT protocol](https://developer.garmin.com/fit/protocol/), [Garmin FIT tools](https://developer.garmin.com/fit/fitcsvtool/), [Suunto decoding example](https://apizone.suunto.com/fit-developer-fields-decoding-example-code).
3. **Exercise downstream contracts.** Run the unchanged Python metrics and chart pipeline for each parity-passing decoder. Compare lap selection, active duration, distance blocks, summaries, observations, and chart series, axes and readouts. Require exact equality for categorical, timestamp and missing-data fields, with documented per-metric tolerances for floating-point values. Compare semantic chart output and browser interactions. For any bridge or access pilot, add stubbed expiry and concurrent refresh, rotated and omitted refresh tokens, one-shot 401 replay, invalid grant, 403, 429 with both header forms, transient failures, cancellation, and unsuccessful artifact publication. Drive the existing worker and SQLite store to verify the same visible retry and job transitions.
4. **Decide from end-to-end results.** If startup or JSON handoff dominates, try the in-process Python adapter first. If decoding dominates and the target still needs improvement, benchmark the Go helper against the Python alternatives on the same workload. Agree on a user-visible latency, batch-throughput, or memory target before comparing results. Adopt a replacement only after parity and a repeatable improvement reaching that target, with the current decoder available during the pilot. A decoder gain justifies changing that component. A wider backend change needs its own measured case.
